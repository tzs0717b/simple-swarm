# 系统层加固：集群为什么会烂尾，系统该怎么拦

> 起因：`pelican-3`（6 个 agent、$15 预算）跑完之后，产物是一只**没实现的模板**，
> 主切片从头到尾没人做完，却有人收工了。下面每一条都是那条产线上的**系统病**，
> 修的地方都在系统层（runner / 工具 / 事件投影），**没有改 agent 的提示词**。

## 一、pelican-3 的尸检结论

## 二、四条系统硬机制

### 1. 收工闸（`runner.doneGate`）—— 不许"烂尾式收工"

| 规则 | 触发条件 | 结果 |
|---|---|---|
| 板没清空 | 还有 `available` / `claimed` 未交付的切片 | 拒绝 `done`，并把**它还能做什么**逐条列给它（自己的活 / 没人接的活 / 别人手上没交付的活） |
| 封板后没查证 | 全部交付了，但该 agent 在封板后没有跑过任何 `bash` / `read` | 拒绝 `done`，要求至少亲手复现一次交付证据 |

- 拒绝时**不标 `refused`**：这是流程拦阻，不是一步失败（标了会触发自动重试，白烧钱）。
- 效果：**全队要么把板清空，要么跑到硬闸（maxTurns / 预算）如实失败** —— 不会再出现"界面显示跑完了、产物是模板"。
- 副作用（有意）：`swarm.completed` 从此是个**可信信号**：它落下的前提是每一片都交付过。

### 2. 切片生成器（`slicer.ts`）—— 治"分工太粗"

开跑前，如果板是空的，系统自己按目标切一份**细粒度**切片摆上去（`slice.added` 事件，**不认领**）：

- 核心产物必须拆成 3~6 片小活；
- **耦合的部件留在同一片**（腿末端要一直踩在踏板上 = 一个运动学整体，切开必然对不上 —— 前两轮 pelican 全栽在这）；
- 至少一片是**可机械判定的断言**（带数字阈值）；
- 造工具的切片最多 2 片。

来源优先级：`SWARM_SLICES` 环境变量 → `workspace/<id>/contract.json` → 派工员模型（失败时换 `LLM_FALLBACK_MODELS[0]` 再试一次）→ 优雅退化成空（agent 照旧自己发布）。

**配套**：`publish_slice` 在"板上有没人接的活、自己手上又一片没有"时会被挡下并指向那些活 —— **先接活、再接完了才允许造血**。分工过粗的根源就是人人都想圈一块大的。

### 3. 孤儿切片回收 + 累计失败放弃（`runner.releaseClaims`）

- 失败计数改成**累计**（原来只数"连续"，一次成功就清零 → louis 撞 20 次都没被放弃）。
- agent 被放弃 / 被发信上限按停时，它名下**未交付**的切片自动 `claim.released` 退回板上，等别人接手。
- 实测：`gate-check` 场景 [E] 里，负责人连挂被放弃后，另一人接手上并交付完成。

### 4. 模型故障转移（`runner.modelFor`）

同一个 agent 的模型**累计**失败到 `LLM_FAILOVER_AFTER`（默认 3）次，就换 `LLM_FALLBACK_MODELS` 里的下一个，并留一条 `模型故障转移` 追踪。
上游 400/503 是模型级故障，重试同一个模型只是烧钱。

## 三、配置开关

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `SWARM_DONE_GATE` | 1 | `0` 关掉收工闸（只有测试会用） |
| `SWARM_SLICER` | 1 | `0` 关掉切片生成器 |
| `SWARM_SLICES` | 空 | ``|`` 分隔的手工切片（优先级最高） |
| `SWARM_SLICER_DEBUG` | 空 | `1` 打印派工员模型的原始回复（排查解析失败） |
| `LLM_FALLBACK_MODELS` | 空 | 逗号分隔的故障转移名单 |
| `LLM_FAILOVER_AFTER` | 3 | 累计失败几次换模型 |
| `LLM_MAX_BRAIN_ERRORS_TOTAL` | 6 | 累计失败几次放弃该 agent（并退还其切片） |

## 四、自检

`npm run gate-check`（`scripts/gate-check.ts`，20 项）逐条验这套机制：

```
[A] 自己名下的片没交付 → 不准收工
[B] 别人手上的片没交付 → 也不准收工（验证者不许先撤）
[C] 全部交付 + 封板后查证 → 才允许全员收工（swarm.completed 才落）
[D] 全交付了但没亲自查证 → 先回去验一遍
[E] 负责人被放弃 → 他名下没交付的片退回板上，别人能接
[F] 失败不连续（被成功一次次打断）→ 累计到阈值也该放弃
```

原有 7 个自检（smoke / ws-check / e2e / mail-check / storm-check / agent-check / retry-check）全部保持通过。
mock 大脑已同步成"守规矩的 agent"：封板后会真跑一次复核再收工。

## 五、还没做（已知缺口）

- `complete_slice` 目前只拦"没人认领"的片，**没拦"别人认领的片"** —— 理论上 A 可以替 B 交付。要不要收紧成"只有持有人能交付"还没定（验证者想替人签收时会不方便）。
- 收工闸只认"封板后跑过 bash/read"。真跑一遍和被 `ls` 糊弄过去，系统分不出来 —— 这里靠的是 agent 的自觉 + 邮件里的社会压力，不是密码学。
- 派工员模型是**系统外挂**的一次调用（不是 agent 提示词的一部分）：它挂了不影响开跑，但会退回到"agent 自己发布"的老行为。

## 六、pelican-7 实测补出来的两个坑

### 6.1 一个丢包的响应能冻住整个集群（已修：`LLM_TURN_DEADLINE_MS`）

pelican-5 那轮跑着跑着，`/run` 的 curl 客户端断线了（会话中断）。结果：
`/proc/<pid>/wchan = do_epoll_wait`、`0 个 ESTABLISHED 连接`、事件数 9 小时纹丝不动 ——
**Node 那个 fetch 的 promise 再也没 settle，runner 就永远等在那一轮上**。
Fastify 那边 `/run` 请求还挂着（日志里只有请求行、没有响应行）。

修法：runner 自己给每一轮上硬超时（`withDeadline`），超时按"大脑异常"处理，
这一轮作废、下一轮继续。`LLM_TIMEOUT_MS` 只管**一次** HTTP 调用，
但 `llm.ts` 会重试多次，所以最坏一轮能拖 15 分钟；这层兜底必须由 runner 拿。

### 6.2 切片生成器的重试位置写错了（已修）

第一版把"换模型重试"写在了 `decomposeGoal` **正常返回空**之后，
而首次调用**抛异常**（网关超时）时直接 `return` 了 —— 重试永远走不到。
pelican-6 就是这么退化的：没有细粒度切片，agent 自己造了 3 片，
其中一片又是「创建 pelican_bike.svg 单文件循环动画（含鹈鹕骑自行车）」这种巨型片。
修完之后 pelican-7 在真跑里首次超时、**故障转移模型 gpt-5.6-luna 切出了 7 片**：

```
定义鹈鹕与自行车静态SVG骨架及部件分组层级
编写车轮旋转与车身位移SMIL动画声明并校验方向
编写腿部曲柄踩踏循环动画并锁定脚部与踏板几何耦合      ← 耦合件不拆开
编写喉囊与翅膀微幅起伏动画并校验无穿模
编写背景视差滚动动画并校验与前进速度比例一致
脚-踏板距离全周期采样脚本：任意t距离≤2px                ← 带数字阈值的机械断言
构建Playwright接触表拼图脚本与首尾帧像素零差校验
```

另外新增 `SWARM_SLICER_MODEL`：`auto` 会随机路由，赌运气不可靠，
生产上应该把它钉在一个稳定肯出 JSON 的模型上。

### 6.3 顺手记一笔：模型清单是**会变的**

pelican-6 里 `cli/gemini-3.1-pro-preview` 探针时还能用，跑到一半变 404
（网关当时的清单只剩 87 个模型，和白天那 1051 个完全不是一批）。
该 agent 累计失败 3 次后被放弃（`brain-giveup`），报告里如实写了原因 ——
**这就是"模型级故障不该让人背锅"该有的样子**。

## 七、第二轮：轮换 + 验收闭环（P1/P2/P3）

第一轮的收工闸解决了"早退"，但没解决"**验收没人做**"和"**活卡在一个人手里**"。
第二轮加的是"测试不过就继续造"和"卡住的活要换人"。

### 7.1 P1 验收闭环：把「测试不过继续造」变成系统机制

**认片**：切片名带 `验证/校验/验收/复检/复核/采样/测量/接触表/断言/自检/回归`（或英文 verify/check/test/…）→ 判定为**验收片**。

| 情况 | 系统的动作 |
|---|---|
| 验收片证据里是 ❌/FAIL/失败/未通过/不符/不一致/超差… | **照收留档**（如实报出「没过」本身就是有价值的交付）→ **自动开一片「修复：…」任务** + 全队发信、点名「最近改过产物的人」；留痕「验收未通过（❌ 结论已存档）」 |
| 证据里读不出结论（既无 ✅ 也无 ❌） | **交付被拒**，要求写清 ✅/❌ 与实测数字（没结论的验收 = 没验） |
| 证据里有 ✅/PASS/通过/合格/满足… | 放行，并记下这次 PASS 的**步序** |
| 系统自动开的 `复检：…` 片 | **不能被"产物最后改动者"自己签收**（自己不能给自己盖章） |

**收工闸加了一条**：板上有验收片时，必须存在一次「**晚于产物最后一次改动**」的 PASS 交付。
没有 → 拒绝收工，并且**系统自己往板上开一片 `复检：<谁>最后一次改动之后重跑验收…`**。

这条就是循环发动机：**产物一改，上次的 PASS 立刻作废 → 必须重新验 → 验不过就退回重做**。
集群不会在"交过的片"上结束，只在"验过的产物"上结束。

### 7.2 P2 停滞轮换：卡住的活要换人

| 触发 | 动作 |
|---|---|
| 某片被认领后 **N 步（默认 20）没有任何 productive 动作**（bash/read/write/edit/交付/发布） | 催办：留痕「催办」+ 全员邮件，点名持有人 |
| 再过 N 步还是没动静 | **强制收回**：`claim.released` 退回板上 + 全员邮件「切片换人」+ 留痕「停滞收回」 |

为什么按"有没有动作"而不是"过了多久"：PELICAN 7 里 sarah 把耦合片抱了很久，
但她一直在 read/edit/bash —— 那是正常干活，收回只会帮倒忙。
真正该收的是 louis 那种：模型死了、一个字没动，片却锁在他名下。

### 7.3 这一轮自己踩的两个坑（都是基准选错）

1. **用时间戳判"先后"判不出来**：mock 几步就跑完，`clock()` 秒级精度让"产物改动"和"验收 PASS"
   落进同一秒 → `passAt < artifactAt` 恒为假 → 闸门形同虚设。**改成用单调步序**（`artifactStep` / `passStep`）。
2. **"封板后亲自查证"的基准选错了**：原来是"板子全交付的那一刻"之后才算数，
   但 P1 的复检会把板子**重新打开**，于是那一刻永远回不来 → 全员被这条无解地挡住。
   改成「**产物最后一次改动之后**你有没有亲手跑过/看过」，与闸规则同源，不再打架。

### 7.4 自检

`scripts/gate-check.ts` 从 20 项扩到 **35 项**，新增：

```
[G] 验收片报 FAIL → 交付被拒、退回板上、全队收到点名邮件；重跑 ✅ 才算交付
[H] 验收片证据读不出结论 → 交付被拒
[I] 产物在验收之后又被改 → 收工被挡 + 系统自动开复检；
    复检片不能由产物最后改动者自己签收；换人复检 ✅ 之后才允许全员收工
[J] 认领后长时间没动作 → 先催办、再强制退还回板（分两步，不是一上来就没收）
```

八套自检全绿：smoke / ws-check / e2e / mail-check(116) / storm-check(39) / agent-check(58) / retry-check(12) / gate-check(35)。


### 7.5 真跑（PELICAN 8）暴露的问题与后续

真跑把三个东西照出来了，其中第一条是**设计错误**，已当场改掉：

1. **「验收报 ❌ 就拒收」是错的**（已改）。PELICAN 8 里 sue 如实跑出失败并交付，系统把她的活拒了、片退回板上 —— 测试员白干、片子在板上弹来弹去。用户要的循环是「测试不过 → **继续造**」，不是「把测试员的活扔掉」。现在：❌ 照收留档 → **自动开一片「修复：…」**（幂等：板上已有未交付的修复片就不再开）→ 点名产物最后改动者发信 → 收工闸继续要求「改动之后的新 PASS」。`isVerificationSlice()` 同时加了特判：修复/修正/返工/fix 开头的一律算**干活片**，免得系统把带「验证」字样的修复任务又当成验收片（自我套娃）。
2. **403 / upstream_error 不会触发故障转移**（待办）。PELICAN 8 里 ashley 的 cli/gemini-3.1-pro-preview 先 404（故障转移判据）又 403，三次就被判停摆。现在故障转移只认「模型不存在」；5xx/403 这类**上游抽风**也该在连续 N 次后换模型。
3. **重启后旧认领的停滞判定失效**（待办）。stallSweep() 用的是「本次 run 的步序」，进程重启后 claimStep 是空的，于是重启前被认领、持有人已经不在了的片永远不会被自动收回（只能靠持有人自己放弃 or 别人接管）。修法：认领时刻回落到账本里的 claim_slice trace 时间。

真跑里**生效了的**（都来自账本，不是自评）：

| 现场 | 系统行为 |
|---|---|
| sue 的模型在运行中从网关消失（404）+ 429 | 累计 6 次 → 判定停摆、如实收工、**片退回板上** → eileen 接手 |
| ashley 的模型 404/403 三次 | 同上：退片 → sue 接手 → 又退 → **luther 接手**（同一片三次易主） |
| sue 换模型后继续干活 | **模型故障转移**：DeepSeek-V4-Flash[free] 累计 3 次失败 → gpt-5.6-luna |
| eileen / luther 想收工 | **收工闸挡下**：「板上还有 3/4 片没交付」 |
| 发现车轮坐标、腿部 IK 有问题 | sharon **自己新发布**两片修复任务（涌现式再分工） |
| 认领撞车 | 4 次「认领冲突（换一片）」被正确让路 |
| 复检没过 | **「验收未通过」留痕**（就是第 1 条暴露出来的那次） |

### 7.6 真跑抓到的第一个 P0：一次工具异常打崩整轮 run（已修）

`/run` 在 12:29:08 返回 500，账本从那一刻起完全静止。栈是：

```
EISDIR: illegal operation on a directory, read
  at toolReadFile (src/agent/tools.ts:350)   ← agent 对**目录**调了 read
  at AgentRunner.execute (runner.ts:932)
  at AgentRunner.turn → AgentRunner.run → /run 路由 → 500
```

**一个 agent 的一次错误工具调用，把 6 个 agent 的一整轮全带崩了**（20 分钟、$0.03 白烧，
而且崩得**无声无息**：没有系统留痕、没有邮件、swarm 还显示 live）。修了两层：

1. `toolReadFile`：读目录 → 返回「这是目录，里面是 xxx、yyy」的可观察失败（还能帮模型纠错）；
   读不动 → 返回「读不了：<原因>」。都不再抛。
2. `runner.turn()`：`this.execute()` 整个套 try/catch —— **任何**工具异常都降级成
   「工具执行出错：<原因>，换个做法再来」的观察结果还给大脑。这一层是兜底，
   保证"再烂的工具调用最多浪费一步，不会带走别人"。

回归护栏：gate-check 新增 `[K]` —— 让两个 agent 先 write、再对目录 read、再读文件，
断言「读目录被挡成可观察的失败」「整个 run 没被带走（全员照常收工）」「两片都交付」。
自检从 36 项涨到 **39 项**。

### 7.7 一次误判：所谓"账本静止 17 分钟"其实是 run **正常跑完**（已修可观测性）

症状：账本最后一条停在 `usage.recorded`，之后十几分钟零事件、零错误日志，但 `/api/swarms/:id`
还是 `state=live`，`/run` 请求也没有对应的响应日志 —— 看上去像第 4 次"静默挂死"。

排查（这套手法以后都能用，值得记下来）：

1. `kill -USR1 <node pid>` 打开 inspector（`http://127.0.0.1:9229/json/list`）；
2. CDP `Debugger.enable` + `Debugger.pause` → 调用栈只有 `processTimers`（说明当时没在执行任何用户 JS，
   异步续体挂在某个 await 上）；
3. CDP `Runtime.evaluate` 打探针：`setTimeout(..., 1500)` 后能读到结果 → **定时器是好的**；
   3 秒 CPU 采样 idle 占 99.98% → **没有死循环**；
4. CDP `Runtime.evaluate("Object.getPrototypeOf(setTimeout(function(){},0))")` → `Runtime.queryObjects`
   列出进程里**所有活着的 Timeout**：只有 WS ping(30s)、一个 native(30s)、`fast-timers` tick(499ms) ——
   **没有** `withDeadline` 的 300s 单轮超时定时器。

结论：run 早就不在等模型了，它是**跑完 for 循环退出的**（`outer: for (round = 1; round <= maxTurns; …)`，
出口 `stoppedBy = "max-turns"`），而这条出口**一个事件都不写**。对上账的铁证：调用数增量 = 轮数 × agent 数
（20 轮 × 6 = +120；12 轮 × 6 = +72，实测 +120 / +70 ✓）。客户端的 Node 脚本每次都被 undici 的
5 分钟 headers timeout 先干掉，所以 `/run` 的响应日志也永远等不到 —— 三件事叠在一起就成了"挂死"。

**修复（可观测性）**：run 结束一律补一条系统留痕「本轮跑完：<原因>，共 N 步（每人每轮上限 M 步；
swarm 仍为 live，可继续 /run 续跑）」。以后判断"跑完还是卡死"看这条就行；要判断服务端状态，
**一律用 curl 续跑（`-m 5400`），别用 undici 客户端**。

顺带保留的加固：`SWARM_WATCHDOG_MS`（一步卡住超过阈值就往账本写「看门狗：「卡在哪个阶段」」）
和 `SWARM_FAIL_MODE=rework|reject`（验收报 ❌ 时是"照收+自动开修复片"还是"拒收+退片"）。

事后验证：修复后的第一轮续跑就留下了「本轮跑完：跑满步数上限，共 60 步（每人每轮上限 10 步…）」
—— 10 轮 × 6 个 agent = 60 步，与「调用数 = 轮数 × 人数」的推断完全吻合，诊断成立。

### 7.8 环境事故：网关模型清单瞬变，一次 run 里 5 个 agent 被"未知模型"打死

现场：一轮 run 里 5 个 agent 的收工理由全是

```
模型网关 404：未知模型 "gpt-5.3-codex"。当前可用模型 84 个：agnes-2.0-flash, agnes-2.5-flash, ...
模型网关 503：模型 "gpt-5.5" 的 1 个候选提供商当前都没有可用密钥（可能已冷却/失效）
```

即 keypool 的模型清单在那几十分钟里**换成了另一套上游**（1051 个 gpt-5.x 家族 → 84 个 agnes-* 家族），
而我们写的 `agentModels` + `LLM_FALLBACK_MODELS` 全是旧名字 → **第 3 次失败时连"可换的模型"都没有**。
事后同一接口又回到 1051 个（其中 `available=true` 的只有 85 个，支持工具的 47 个）。

教训与对策：

1. **备用名单必须是"当下实测可用"的名字**，不能照抄历史；换模型前先 `GET /v1/models` 核对，
   再拿一个带 `tools` 的最小请求实测（48 个候选里实测只有 9 个真通）。
2. 已经落地的韧性修（见 7.9）：只要**还有另一个模型可换**，就不在"连续失败"上处决 agent。
3. 待办：`/run` 的预检（模型不在网关清单里就直接 400，并把清单里的可用替代品回给调用方），
   别再让一整轮 run 拿 6 个死模型空转。
